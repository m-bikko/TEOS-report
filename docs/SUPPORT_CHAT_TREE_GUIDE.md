# Дерево частых вопросов в чате техподдержки

Гайд по демо-стенду для бэкенда и мобильной команды. Покрывает задачи **BE-01…BE-05**.
Задача BE-06 (импорт/экспорт) на стенде не показана — по решению заказчика вкладку убрали,
но формат выгрузки описан в разделе 4 и остаётся в силе.

Прототипы:

| Страница | Что показывает |
|---|---|
| `/support-mobile` | как дерево выглядит в приложении исполнителя; фрейм №2 — кликабельное демо |
| `/support-chat-builder` | конструктор дерева в web-ERP: черновик, валидация, публикация |
| `/support-admin` | что видит оператор, когда обращение пришло из дерева |

Весь код на мок-данных, ничего не персистится.

Контент двуязычный: `title_ru`/`title_kz` и `body_ru`/`body_kz`, как в BE-01. В редакторе
поля идут парами ru/kz бок о бок, пропуск подсвечивается меткой «нет перевода».
Казахские строки на стенде — черновой перевод, до прода нужна вычитка носителем.

---

## 1. Поток

1. Пользователь открывает обращение — вместо формы стартует тред с помощником.
2. Помощник показывает корневое меню. Каждый пункт (`MENU`) раскрывает следующий уровень.
   **Глубина не ограничена** ни в модели, ни в интерфейсе.
3. Лист (`ANSWER`) выдаёт готовый текст с пометкой **«Автоответ»**.
4. Под ответом: «Спасибо, помогло» — обращение закрывается без оператора; «Не помогло,
   нужен оператор» — тред передаётся живой техподдержке.
5. После передачи сообщения оператора идут в том же треде с пометкой **«Техподдержка»**.

Пользователь в любой момент видит, кто ему отвечает: бот и оператор помечены по-разному.
Это требование интерфейса, а не деталь вёрстки.

---

## 2. Модель узла

Демо повторяет `support_chat_node` из BE-01 один в один:

| Колонка БД | Поле в демо | Комментарий |
|---|---|---|
| `id` | `id` | uuid |
| `parent_id` | `parentId` | `null` — корень |
| `node_type` | `nodeType` | `MENU` \| `ANSWER` |
| `sort_order` | `sortOrder` | порядок внутри одного уровня |
| `is_active` | `isActive` | выключенный узел не отдаётся приложению |
| `title_ru` | `titleRu` | подпись кнопки |
| `title_kz` | `titleKz` | то же по-казахски; пусто — приложение покажет русский |
| `body_ru` | `bodyRu` | текст автоответа, только у `ANSWER` |
| `body_kz` | `bodyKz` | то же по-казахски |
| `icon` | `icon` | имя иконки lucide, см. `_support-shared/icons.tsx` |
| `action_type` | `actionType` | см. раздел 3 |
| `action_payload` | `actionPayload` | форма зависит от `action_type` |
| `updated_by` | `updatedBy` | кто правил в админке |

Узлы хранятся **плоским списком** — как строки таблицы. Вложенность собирается на лету.
Это сделано специально: так видно, что именно летит в БД, и почему BE-04 нужен отдельным
массовым запросом.

Код: [`src/app/_support-shared/chatTree.ts`](../src/app/_support-shared/chatTree.ts).

## 3. Справочник `action_type`

Набор не был зафиксирован в постановке — предложен на стенде. Каждое значение
соответствует ровно одному элементу интерфейса под текстом ответа.

| `action_type` | `action_payload` | Поведение в приложении |
|---|---|---|
| `NONE` | `{}` | ничего, ветка кончается текстом |
| `ESCALATE` | `{ "category": "executor" \| "b2b" }` | кнопка передачи обращения оператору; создаётся тикет в указанной категории |
| `OPEN_LINK` | `{ "url": "...", "labelRu": "...", "labelKz": "..." }` | кнопка-ссылка на внешнюю инструкцию |
| `OPEN_SCREEN` | `{ "screen": "...", "labelRu": "...", "labelKz": "..." }` | диплинк внутрь приложения |
| `CALL_CENTER` | `{ "phone": null }` | кнопка звонка; `null` — номер берётся из настроек |

Список экранов для `OPEN_SCREEN` согласуется с мобильной командой; в демо он лежит в
константе `APP_SCREENS`.

`ESCALATE` обязателен хотя бы в одной ветке каждого раздела — иначе пользователь
не сможет дойти до живого человека. Это проверяется валидацией (раздел 5).

## 4. Контракт `GET /support-chat/tree` (BE-02)

Ответ — опубликованная версия целиком, одним запросом, с `ETag`.

```json
{
  "version": 3,
  "settings": {
    "greeting": "Здравствуйте! Подскажу по частым вопросам…",
    "fallback_text": "Не нашли свой вопрос? Опишите проблему…",
    "contact_phone": "+7 (707) 741-89-65",
    "contact_email": "support@teos.kz",
    "btn_helped": "Спасибо, помогло",
    "btn_escalate": "Не помогло, нужен оператор",
    "btn_back": "Назад"
  },
  "nodes": [
    {
      "id": "00000000-0000-4000-8000-00000000000b",
      "parent_id": null,
      "node_type": "MENU",
      "sort_order": 1,
      "is_active": true,
      "title_ru": "Оплата и начисления",
      "body_ru": null,
      "icon": "Wallet",
      "action_type": "NONE",
      "action_payload": null
    },
    {
      "id": "00000000-0000-4000-8000-00000000000e",
      "parent_id": "00000000-0000-4000-8000-00000000000c",
      "node_type": "ANSWER",
      "sort_order": 1,
      "is_active": true,
      "title_ru": "Прошло больше 3 рабочих дней",
      "body_ru": "Срок вышел — нужна проверка…",
      "icon": null,
      "action_type": "ESCALATE",
      "action_payload": { "category": "executor" }
    }
  ]
}
```

Приложение получает **плоский список** и строит дерево у себя — так дешевле
диффать и кэшировать по `ETag`. Неактивные узлы в выдачу не попадают.

Ровно такой JSON (без `version`) отдаёт вкладка «Импорт-экспорт» конструктора —
можно скачать файл и использовать как фикстуру.

## 5. Валидация (BE-03, BE-06)

Одинаковая для CRUD и для импорта.

| Правило | Уровень |
|---|---|
| `ANSWER` не может иметь потомков | ошибка |
| Узел не может быть собственным предком (цикл) | ошибка |
| `MENU` без активных потомков — пустой экран у пользователя | ошибка |
| Пустой `title_ru` | ошибка |
| `ANSWER` с пустым `body_ru` | ошибка |
| В ветке нет ни одного достижимого `ESCALATE` | предупреждение |
| Нет казахского перевода заголовка или текста | предупреждение |

Ошибки блокируют публикацию версии, предупреждения — нет.

В конструкторе замечания показываются под деревом; клик по замечанию выделяет узел.

## 6. Перенос узлов (BE-04)

Перетаскивание в конструкторе всегда формирует **один патч** — список затронутых узлов
с новыми `parent_id` и `sort_order`. Промежуточных состояний не возникает: при переносе
перенумеровываются оба уровня — и тот, откуда узел ушёл, и тот, куда пришёл.

```json
PATCH /admin/support-chat/reorder
[
  { "id": "…0e", "parent_id": "…0c", "sort_order": 0 },
  { "id": "…0d", "parent_id": "…0c", "sort_order": 1 },
  { "id": "…0f", "parent_id": "…0b", "sort_order": 1 }
]
```

Конструктор показывает получившийся патч строкой над редактором — можно сверить формат.

Побочное правило: если узел переносят внутрь `ANSWER`, целевой узел автоматически
становится `MENU`. Иначе сразу возникла бы ошибка валидации.

## 7. Версии (BE-01)

Черновик редактируется свободно; приложение видит только версию со статусом `PUBLISHED`.

- Публикация создаёт новую запись `support_chat_version` со снапшотом всего дерева
  и переводит предыдущую в `ARCHIVED`.
- Кнопка публикации блокируется при ошибках валидации и когда черновик не отличается
  от опубликованной версии.
- Откат версии в черновик остаётся задачей бэкенда; на стенде список версий не показан —
  в шапке видно только состояние текущего черновика.

## 8. Сообщения в чате

Тип автора расширен третьим значением:

```ts
type MessageAuthor = "user" | "support" | "bot";
```

Сообщение бота дополнительно несёт:

| Поле | Когда заполнено | Зачем |
|---|---|---|
| `kind` | всегда у бота | `menu` — список вариантов, `answer` — конечный ответ |
| `nodeId` | всегда у бота | из какого узла дерева сообщение |
| `options` | `kind = "menu"` | пункты следующего уровня |
| `actions` | `kind = "answer"` | кнопка действия узла |
| `pickedNodeId` | у сообщения пользователя | какой пункт он нажал |

Тикет получает два поля:

- `treePath: string[]` — цепочка `nodeId` от корня до узла эскалации. Оператор видит её
  в карточке обращения и не переспрашивает то, что бот уже сказал.
- `resolvedByBot: boolean` — обращение закрылось автоответом, оператор не подключался.
  На этом считается метрика «решено автоответом» на канбан-доске.

## 9. Что осознанно не сделано на стенде

- Список версий и откат — вкладку убрали, задача остаётся за бэкендом (BE-01).
- Импорт/экспорт JSON — вкладку убрали, контракт BE-06 описан в разделе 4.
- Персистентность конструктора — состояние живёт в памяти вкладки.
- Поиск по базе знаний внутри чата.
- Условные переходы по данным пользователя — под них нет полей в BE-01.
- Аналитика по узлам (какая ветка чаще помогает) — отдельная задача.
