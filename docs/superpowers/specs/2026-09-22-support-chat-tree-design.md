# Дерево частых вопросов в чате техподдержки + ERP-конструктор

**Дата:** 2026-09-22
**Статус:** дизайн утверждён, ожидает плана реализации
**Затрагивает:** `/support-mobile`, `/support-admin`, новая страница `/support-chat-builder`

---

## 1. Задача

Сейчас обращение в техподдержку — это сразу переписка с живым оператором. Нужно поставить
перед оператором автоматическую ступень: пользователь открывает обращение и попадает в
дерево частых вопросов. Каждый пункт раскрывает следующий уровень, глубина не ограничена.
Конечный узел выдаёт готовый ответ с явной пометкой **«Автоответ»**. Если ответ не помог —
тот же тред подхватывает живой оператор, и его сообщения помечаются **«Техподдержка»**.

Вторая половина задачи — страница в web-ERP, на которой это дерево собирают: CRUD узлов,
перетаскивание, публикация версий, настройки, импорт/экспорт.

**Для кого:** демо-стенд для согласования с командой и бэкендом. Все страницы работают на
мок-данных, ничего не персистится. Прод-реализацию делает бэкенд по задачам BE-01…BE-06.

**Критерий успеха:** по этим страницам бэкенд видит формат `support_chat_node`, мобильная
команда — поведение чата, а продукт может прокликать дерево произвольной глубины живьём.

### Выбранный вариант потока

Из трёх рассмотренных вариантов выбран **А — дерево внутри чата, эскалация в конце**:

- нажатие «+» открывает не форму, а тред с ботом;
- пользователь идёт по веткам, получает автоответ с пометкой «Автоответ»;
- под ответом «Помогло → закрыть» и «Не помогло → позвать техподдержку»;
- при эскалации тот же тикет подхватывает оператор, история выбора видна ему целиком.

Отвергнуты: вариант Б (дерево отдельным разделом «База знаний» — теряется контекст для
оператора) и вариант В (дерево как предфильтр перед формой — две разные сущности вместо
одной ленты сообщений).

### Ограничения, заданные заказчиком

1. **Один язык.** Демо только на русском. В контракте BE-01 есть `title_kz` / `body_kz`, но
   переключатель языков в проекте живёт в другом месте — в демо его не делаем и в мок-модель
   поля `*_kz` не добавляем.
2. **Контракт бэкенда задан** задачами BE-01…BE-06 (структура таблиц, эндпоинты, ETag,
   валидация, версии, импорт/экспорт). Демо обязано ему соответствовать, а не изобретать своё.
3. **Набор `action_type` не зафиксирован** тех-лидом — определяется в этом документе.

## 2. Модель данных

Новый файл `src/app/_support-shared/chatTree.ts`.

Узлы хранятся **плоским массивом**, как в таблице `support_chat_node`, а не вложенным
деревом. Это осознанно: демо должно показывать бэкенду ровно то, что лежит в БД, и делать
очевидным смысл BE-04 (массовое обновление `parent_id` / `sort_order` одним запросом).
Вложенность строится на лету хелпером `childrenOf`.

```ts
export type NodeType = "MENU" | "ANSWER";

export type ActionType =
    | "NONE"
    | "ESCALATE"
    | "OPEN_LINK"
    | "OPEN_SCREEN"
    | "CALL_CENTER";

export type ActionPayload =
    | { kind: "NONE" }
    | { kind: "ESCALATE"; category: TicketCategory }
    | { kind: "OPEN_LINK"; url: string; label: string }
    | { kind: "OPEN_SCREEN"; screen: string; label: string }
    | { kind: "CALL_CENTER"; phone: string | null };

export interface SupportChatNode {
    id: string;                        // uuid
    parentId: string | null;           // null = корень
    nodeType: NodeType;
    sortOrder: number;
    isActive: boolean;
    title: string;                     // title_ru
    body: string | null;               // body_ru, заполнен только у ANSWER
    icon: string | null;               // имя иконки lucide-react
    actionType: ActionType;
    actionPayload: ActionPayload | null;
    updatedBy: string;
    updatedAt: string;                 // ISO
}
```

Соответствие контракту BE-01: `node_type` → `nodeType`, `sort_order` → `sortOrder`,
`is_active` → `isActive`, `title_ru` → `title`, `body_ru` → `body`, `action_type` →
`actionType`, `action_payload` → `actionPayload`, `updated_by` → `updatedBy`. Поля
`title_kz` / `body_kz` в демо отсутствуют (см. ограничение 1).

### Настройки (BE-05)

```ts
export interface SupportChatSettings {
    greeting: string;        // первое сообщение бота
    fallbackText: string;    // когда подходящей ветки нет
    contactPhone: string;    // контакт-центр, дефолт для CALL_CENTER
    contactEmail: string;
    btnHelped: string;       // «Спасибо, помогло»
    btnEscalate: string;     // «Не помогло, нужен оператор»
    btnBack: string;         // «Назад»
}
```

### Версии (BE-01)

```ts
export interface SupportChatVersion {
    id: number;
    version: number;
    status: "PUBLISHED" | "ARCHIVED";
    publishedAt: string;
    publishedBy: string;
    nodeCount: number;
    snapshot: SupportChatNode[];
}
```

### Направление импортов

`chatTree.ts` не импортирует ничего из `mockData.ts`. Иначе получается цикл: `ESCALATE`
нужен `TicketCategory`, а `ChatMessage.actions` нужны `ActionType` и `ActionPayload`.
Поэтому `TicketCategory` **переезжает** в `chatTree.ts`, а `mockData.ts` его реэкспортирует:

```ts
// mockData.ts
export type { TicketCategory } from "./chatTree";
```

Существующие импорты `TicketCategory` из `mockData` (используется в `support-admin/page.tsx`)
продолжают работать без правок. Зависимость односторонняя: `mockData` → `chatTree`.

### Хелперы

| Функция | Назначение |
|---|---|
| `childrenOf(nodes, parentId)` | дети узла, отсортированы по `sortOrder`, неактивные отфильтрованы флагом |
| `pathTo(nodes, id)` | цепочка от корня до узла — хлебные крошки и `treePath` тикета |
| `reorder(nodes, nodeId, newParentId, newIndex)` | возвращает патч `{ id, parentId, sortOrder }[]` — ровно то, что ждёт BE-04 |
| `validateTree(nodes)` | список замечаний, те же правила, что в BE-03 |
| `exportTree(nodes, settings)` / `importTree(json)` | формат BE-06, с той же валидацией |

### Правила валидации

Повторяют BE-03 и BE-06:

1. `ANSWER` не может иметь потомков.
2. Циклы запрещены (узел не может быть собственным предком).
3. `MENU` без активных потомков — тупик, замечание.
4. Пустой `title` — ошибка.
5. `ANSWER` с пустым `body` — ошибка.
6. Ветка, из которой недостижим ни один `ESCALATE`, — предупреждение (пользователь не
   сможет позвать оператора).

Ошибки блокируют публикацию, предупреждения — нет.

## 3. Набор `action_type`

Тех-лид зафиксировал только дефолт `NONE` и наличие `action_payload json`. Набор ниже —
решение этого дизайна; каждое значение соответствует ровно одному элементу интерфейса под
текстом ответа.

| Значение | `action_payload` | Что рисуется под ответом |
|---|---|---|
| `NONE` | — | ничего, ветка кончается текстом |
| `ESCALATE` | `{ category }` | «Не помогло → позвать техподдержку»; тред уходит живому оператору |
| `OPEN_LINK` | `{ url, label }` | кнопка-ссылка (как «Инструкция по обновлению санкнижки») |
| `OPEN_SCREEN` | `{ screen, label }` | диплинк внутрь приложения: «Открыть профиль» |
| `CALL_CENTER` | `{ phone }` | «Позвонить»; при `phone: null` берётся `contactPhone` из настроек |

`ESCALATE` обязателен — без него вариант А не работает, тупиковая ветка никуда не ведёт.
`CALL_CENTER` оправдывает поле «контакты контакт-центра» в BE-05.

## 4. Сообщения: третий автор

Правка `src/app/_support-shared/mockData.ts`.

```ts
export type MessageAuthor = "user" | "support" | "bot";
```

`ChatMessage` получает необязательные поля — существующие 15 сообщений остаются валидными:

```ts
export interface ChatMessage {
    // ...существующие поля без изменений
    kind?: "text" | "menu" | "answer";      // по умолчанию "text"
    nodeId?: string;                        // узел дерева, породивший сообщение
    options?: { nodeId: string; title: string; icon: string | null }[];
    actions?: { type: ActionType; label: string; payload: ActionPayload }[];
}
```

`Ticket` получает `treePath?: string[]` — цепочка `nodeId` от корня до узла, на котором
пользователь эскалировал. Оператор в ERP видит её сразу и не переспрашивает.

### Отрисовка пометок

Ключевое требование заказчика — пользователь всегда понимает, кто ему отвечает.

| Автор | Пузырь | Пометка | Аватар |
|---|---|---|---|
| `user` | синий, справа | — | — |
| `bot` | серый, слева | бейдж **«Автоответ»** | иконка робота, без имени |
| `support` | белый, слева | бейдж **«Техподдержка»** | аватар + имя оператора |

Момент передачи оператору показывается разделителем в ленте: «Передано оператору · 18:31».

## 5. Мобильный экран `/support-mobile`

Страница остаётся витриной состояний в рамках телефона. Добавляются фреймы:

1. **Стартовое меню бота** — приветствие из настроек + корневые пункты с иконками.
2. **Вложенное меню** — хлебные крошки «Оплата › Не пришли деньги», кнопка «Назад».
3. **Конечный автоответ** — бейдж «Автоответ», текст, кнопка действия (`OPEN_LINK`),
   ниже «Помогло» / «Не помогло».
4. **Эскалация** — тот же тред: сверху история бота, разделитель «Передано оператору»,
   ниже сообщения с бейджем «Техподдержка».

Плюс **один интерактивный фрейм** (`BotChatDemo.tsx`, клиентский компонент): по дереву
можно реально кликать на любую глубину, с «Назад» и сбросом. Статические фреймы не могут
показать произвольную вложенность — а это суть фичи; заодно интерактив проверяет, что
модель рабочая.

Существующие фреймы (список обращений, активный чат, прикрепления, закрытый тикет)
сохраняются.

`PhoneFrame` выносится из `support-mobile/page.tsx` в `_support-shared/PhoneFrame.tsx` —
он нужен ещё и в превью конструктора.

## 6. ERP: страница `/support-chat-builder`

Клиентская страница, состояние в памяти, ничего не персистится. Три колонки, сверху
вкладки и кнопка публикации.

```
┌ Техподдержка › Конструктор чата        [Черновик · 4 изм.]  [Опубликовать] ┐
│ Дерево │ Настройки │ Версии │ Импорт-экспорт                               │
├──────────────────┬────────────────────────────┬───────────────────────────┤
│ ДЕРЕВО           │ РЕДАКТОР УЗЛА              │ ПРЕВЬЮ                    │
│                  │                            │                           │
│ ▾ Оплата      ⠿  │ Оплата › Не пришли деньги  │  ┌───────────┐            │
│   ▾ Не пришли ⠿  │                            │  │ ← Поддержка│            │
│     • Ответ   ⠿  │ Тип     (MENU) (ANSWER)    │  │           │            │
│   • Неверная  ⠿  │ Заголовок […]              │  │ Бот:      │            │
│ ▸ Смены       ⠿  │ Текст     […]              │  │ Что с     │            │
│ ▸ Документы   ⠿  │ Иконка    […]              │  │ оплатой?  │            │
│                  │ Активен   [x]              │  │ › Не приш.│            │
│ [+ узел]         │ Действие  [ESCALATE ▾]     │  │ › Неверная│            │
│                  │ Категория [Исполнитель ▾]  │  └───────────┘            │
│ ⚠ 2 замечания    │                            │                           │
└──────────────────┴────────────────────────────┴───────────────────────────┘
```

### Панель дерева (слева, ~300px)

- Вложенный список с отступами; `MENU` — раскрывающийся, `ANSWER` — лист.
- **Drag-and-drop на нативном HTML5 API**, без новых зависимостей: бросок *на* узел делает
  его дочерним, бросок *между* узлами меняет порядок. Каждый бросок формирует патч через
  `reorder()` и показывает его в консоли демо — это наглядная иллюстрация BE-04.
- Стрелки ↑↓ остаются как доступный запасной путь для тех, кому перетаскивание недоступно.
- Действия узла: добавить соседа, добавить потомка, дублировать, удалить, переключить
  активность. Неактивные узлы приглушены.
- Внизу — панель валидации: ошибки красным, предупреждения жёлтым, клик ведёт к узлу.

### Редактор узла (центр)

Хлебные крошки пути, затем форма: тип (`MENU`/`ANSWER`), заголовок, текст ответа (только
для `ANSWER`), иконка, активность, `action_type`. Блок `action_payload` перерисовывается
под выбранный тип действия. Смена типа с `MENU` на `ANSWER` при наличии потомков
блокируется с объяснением (правило валидации 1).

### Превью (справа, ~360px)

`PhoneFrame` с живым рендером выбранного узла — ровно тот же компонент, что на
`/support-mobile`. Меняется при выборе узла в дереве.

### Вкладки

| Вкладка | Содержимое | Задача бэка |
|---|---|---|
| Дерево | описанное выше | BE-03, BE-04 |
| Настройки | приветствие, fallback, контакты, подписи кнопок | BE-05 |
| Версии | таблица `PUBLISHED` / `ARCHIVED`, откат версии в черновик | BE-01 |
| Импорт-экспорт | JSON контракта в textarea, скачать / загрузить, ошибки валидации | BE-06 |

### Публикация

Кнопка «Опубликовать» в шапке: блокируется при наличии ошибок валидации, показывает
сводку изменений относительно текущей опубликованной версии, создаёт новую запись
`SupportChatVersion` со снапшотом и переводит предыдущую в `ARCHIVED`.

В сайдбар добавляется пункт «Техподдержка → Конструктор чата» (`activeKey: "chat-builder"`).

## 7. Канбан админа `/support-admin`

Небольшая правка: в модале тикета, пришедшего из дерева, показывается блок «Путь по
дереву» — хлебные крошки из `treePath` и текст автоответа, который пользователь уже
получил. Оператор сразу видит, что бот уже сказал, и не повторяется.

## 8. Мок-дерево

28 узлов, максимальная глубина 4 — достаточно, чтобы показать «неизвестно сколько
вложений». Темы взяты из существующих тикетов в `mockData.ts`.

```
Смены
├── Не могу записаться на смену
│   ├── Кнопка «Записаться» неактивна          → OPEN_SCREEN profile.documents
│   ├── Запись отклонена
│   │   ├── Просрочена санкнижка               → OPEN_LINK инструкция
│   │   ├── Не указан ИИН                      → OPEN_SCREEN profile.main
│   │   └── Другая причина                     → ESCALATE
│   └── Смена пропала из списка                → NONE
├── Опоздал или не смог выйти                  → CALL_CENTER
└── Как отметиться на смене                    → OPEN_LINK

Оплата и начисления
├── Не пришли деньги за смену
│   ├── Прошло меньше 3 рабочих дней           → NONE
│   └── Прошло больше 3 рабочих дней           → ESCALATE
├── Неверная сумма начисления                  → ESCALATE
└── Как посмотреть историю выплат              → OPEN_SCREEN

Документы и АВР
├── Как подписать АВР                          → OPEN_LINK
├── Не приходит СМС с кодом подписания
│   ├── Проверьте номер в профиле              → OPEN_SCREEN profile.main
│   └── Номер верный, СМС не приходит          → ESCALATE
└── Где скачать справку о доходах              → OPEN_SCREEN

Профиль и доступ
├── Не могу войти в приложение
│   ├── Забыл пароль                           → OPEN_SCREEN auth.reset
│   └── Аккаунт заблокирован                   → ESCALATE
├── Как обновить санкнижку                     → OPEN_LINK
└── Изменить номер телефона  [неактивен]       → ESCALATE
```

Узел «Изменить номер телефона» выключен намеренно — демонстрирует `is_active: false` и
приглушённый вид в конструкторе.

## 10. Проверка

Автотестов в проекте нет — фреймворк не подключён, заводить его ради демо-страниц не
входит в задачу. Проверка:

1. `npm run build` — сборка без ошибок типов.
2. `npm run lint` — без новых замечаний.
3. Ручной проход по `/support-mobile`: интерактивный фрейм проходится до листа любой
   ветки, «Назад» возвращает на уровень выше, бейджи «Автоответ» и «Техподдержка»
   различимы.
4. Ручной проход по `/support-chat-builder`: создание узла, перетаскивание между уровнями,
   смена `action_type`, срабатывание каждого правила валидации, экспорт → импорт того же
   JSON даёт то же дерево.

Строгая типизация обязательна: `any` не используется, `ActionPayload` — размеченное
объединение по `kind`.

## 11. Что осознанно не делается

- **Переключатель языков** — по прямому указанию заказчика; `*_kz` в демо-модель не входит.
- **Персистентность** — состояние конструктора живёт в памяти вкладки, как в остальных
  демо-страницах стенда.
- **Поиск по дереву в мобильном чате** — существующая строка поиска ищет по обращениям;
  поиск по базе знаний не заказан.
- **Ветвление по данным пользователя** (условные переходы, переменные) — в контракте
  BE-01 нет полей под это.
- **Аналитика по узлам** (сколько раз ветка помогла) — отдельная задача, в BE-01…BE-06
  не заложена.
